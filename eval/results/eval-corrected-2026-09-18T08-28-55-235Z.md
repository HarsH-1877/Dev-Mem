## Token Accounting Methodology

Every token figure is derived from `Math.ceil(text.length / 4)` applied to
actual content strings. No flat per-task multipliers are used anywhere.

Per-task token components (same categories for both modes):
- **base** = system prompt + task instruction text + agent response text
  (identical in both modes — the agent must still answer the task either way)
- **injection** = ON mode only: `generateInjectionString()` output, char-counted
- **rediscovery** = OFF mode only: per-dependency, the concrete tool-call text
  (file read + grep output) + the re-derived conclusion text, char-counted.
  Each exchange is defined explicitly in the task definition — no multiplier.

Net token delta = OFF_total − ON_total (positive = Dev-Mem saves tokens).
No post-hoc adjustments are made to either side after counting.

**Eval retrieval budget: adaptive default (shipped `adaptiveBudget(nodeCount)`).**
This run uses *no* override — `retrieveContext` is called without `budgetTokens`,
so it applies the exact same adaptive default a real user gets:
`clamp(nodeCount × 18, 80, 2000)` computed live from the graph at each session.
This is NOT a fixed placeholder — it is the actual shipped default under test.

**Time-to-completion** values are wall-clock from this simulated harness run.
They reflect git ops, SQLite writes, and extraction mock latency — NOT real
LLM inference latency. Do not compare to real Claude Code session times.
